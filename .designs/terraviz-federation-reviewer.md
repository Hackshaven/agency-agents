- **Track and home:** Fork only. It lives on `hackshaven` and never rides in an upstream PR, because its subject is one NOAA project's wire contract. File `engineering/engineering-terraviz-federation-reviewer.md`; skill name `agency-terraviz-federation-reviewer`.
  - **The name** matches the roster row the TerraViz runbook already reserves (Review Gates in `strategy/runbooks/scenario-terraviz.md`). "TerraViz Contract Reviewer" would describe the scope a little better, since the scope includes the embed URL grammar. But the runbook, its Key Decisions table, and commit `4ebc1d7` all say "Federation Reviewer," and the federation wire is the center of the job.
  - **Engineering**, beside the API Platform Engineer and the Code Reviewer, whose boundaries it shares.
  - **It replaces the repo-local `federation-protocol-reviewer`** the first runbook assumed. That agent exists on no branch (commit `4ebc1d7`); it turned out to be Eric's own, uncommitted, in his local TerraViz checkout, and Revision 2 below folds in what it had that this one lacked. Unlike TerraViz's `analytics-reviewer`, this one ships in the catalog. So it finds the checkout, rereads the docs from it, and assumes nothing about living inside it.
- **Who uses it:** Eric, as TerraViz's one maintainer (`GOVERNANCE.md:18-22`), on every PR that touches a published contract. Later, a second maintainer. Possibly operators of partner forks who want to confirm a local change still speaks the canonical contract. Narrow: mostly Eric.
- **Can Eric validate it himself:** Mostly yes, because the question is mechanical once you frame it as the reader test. Apply a patch, feed the new output to an existing reader's code, and see what it does. The test kit does exactly that. Its ground truth was settled by running code: the SPA's region filter against both bounding-box forms, and the node-identity validator against 2,000 generated keys. Three things need more than Eric's own check:
  - which of the two versioning policies governs (finding 3), which is Eric's decision to make, not to verify
  - whether unknown third-party readers exist, which nobody can know
  - Phase 4 signature code, which needs a cryptography-literate human or the Application Security Engineer

  `GOVERNANCE.md:241-244` already says AI review is partial, and models share errors (Kim et al., ICML 2025: on one leaderboard, when two models both erred, they agreed 60% of the time). So on identity changes a human, or a different model, still counts for more.
- **Closest catalog agents and boundaries** (checked 2026-10-05 against the 290 agents on `hackshaven`; the four handoff agents confirmed in `origin/hackshaven`):
  - **API Platform Engineer** designs and builds public APIs: contract-first OpenAPI, versioning, SDKs, gateways. Its compatibility table matches this agent's classes and says a new enum value is safe only "if clients tolerate unknowns — document this!" (`engineering/engineering-api-platform-engineer.md`). But it doesn't know TerraViz's docs, the plugin, or the identity model. It isn't read-only, and it has no procedure for a change whose type stays put while its meaning moves. Boundary: it keeps the publish API, the Orbit postMessage bridge, and STAC-only changes. This agent takes the contracts `GOVERNANCE.md:130` lists as published: `/schema/v1`, the embed URL grammar, and the federation feed, plus discovery and identity. It flags STAC only where a shared type crosses over.
  - **Code Reviewer** lists "Breaking API contracts" as a blocker but has no way to know what TerraViz's contract is, or who reads it. It stays the default reviewer and the second reviewer on identity and signing (the runbook's high-scrutiny rule).
  - **Scientific Visualization Reviewer** owns what a `ColorScale` claims about pixels. This agent owns whether a reader of the wire still decodes it.
  - **Application Security Engineer and Security Architect** own cryptography and trust design. This agent owns compatibility of the identity format.
  - **API Tester and Test Automation Engineer** run tests. They don't judge compatibility.
  - Nothing in the catalog reviews one project's wire contract against that project's own versioning rules.
- **Outside the catalog** (TerraViz's own checks, and what each leaves open):
  - `check:protocol-schemas` (`scripts/build-protocol-schemas.ts`, in the `type-check` chain, `package.json:41`) catches drift between the types and the JSON. It passes on a rename or removal once the author regenerates, and it can't see a meaning change.
  - The `guard-protected-files` hook (`.claude/hooks/guard-protected-files.mjs:73-76`) blocks hand edits to `public/schema/v1/*.json`.
  - `check:migrations` checks only that D1 migrations are additive.
  - The plugin's smoke test (`tests/smoke/PublicApiSmokeTest.php:43-56`) asserts four dataset fields against the live node.
  - None of them checks semantics, CHANGELOG discipline, the SPA's inbound copy, version-marker agreement, or the identity format. `CODEOWNERS` routes nothing (finding 12).
  - The agent's discipline is modeled on `.claude/agents/analytics-reviewer.md`: reread the authoritative doc each run ("the document wins"), PASS/FAIL/UNCONFIRMED, `file:line` on every finding, loud escalation, scope limited to the diff.
- **Origins:** Eric's request, 2026-10-05: build the reviewer the runbook assumed, as a fork-only catalog agent. Research the same day covered TerraViz `main` at `3e3aae5`, with history from a blobless clone; the WordPress plugin at `68ac053`; and the catalog. What shaped the rules:
  - **The repo's own history.** Four commits changed `public/schema/v1/*.json` without a CHANGELOG entry (finding 1); this is Rule 11 and the CHANGELOG line of the checklist. `c6df948a` shipped an optional field that changes what `vmin` means (finding 2); this is Rule 6. `e3655437`'s commit message documents the SPA mapping blind spot ("a field simply absent from the mapping is not an error… shipped green"); this is the checklist's SPA line.
  - **Compatibility in both directions**, because nodes upgrade on their own schedules and the protocol pins versions per peer (`CATALOG_FEDERATION_PROTOCOL.md:418-421`). This is Rule 4.
  - **Breaks are common and deliberate.** About 15% of API changes break compatibility, and the rate grows over time (Xavier, Brito, Hora & Valente, SANER 2017). Developers break APIs mostly to add features, simplify, or improve maintainability (Brito, Xavier, Hora & Valente, SANER 2018), so "cleanup" and "refactor" PRs get read hunk by hunk. These are Rules 4 and 12, and scenario S3.
  - **Correlated model errors** (Kim, Garg, Peng & Garg, ICML 2025) and `GOVERNANCE.md` §Review of AI-assisted changes: the partial-measure line and the second reviewer on identity changes (Rules 8 and 13).
  - **Governance:** a backward-incompatible change to a published contract, or a change to the node identity model, is consequential and needs every active maintainer's agreement (`GOVERNANCE.md:59-69`). This is Rules 3 and 8, and the escalation trigger.
- **Findings for Eric** (about TerraViz and the runbook, not agent rules; each checked 2026-10-05 against `3e3aae5`):
  1. **The protocol CHANGELOG has missed every schema change since v1.** `docs/protocol/CHANGELOG.md` has one entry, v1 of 2026-07-04, plus a 2026-09-08 wording edit. Since then, four commits changed `public/schema/v1/{dataset,catalog}.schema.json`, each without an entry:
     - `0947eca7` (2026-07-27) added `renderEncoding` and `colorScale`
     - `97a9c6da` (2026-07-27) typed both
     - `c6df948a` (2026-07-31) added `colorScale.dataMinLuma`
     - `e3655437` (2026-08-18) added `playbackFps`

     `docs/protocol/README.md:54-56` requires an entry. Nothing enforces it, and the plugin's "regenerate in the same week" practice depends on those entries.
  2. **`dataMinLuma` changed a meaning and shipped as additive.** The data-encoded mapping becomes `vmin + ((luma − lo)/(255 − lo))·(vmax − vmin)` (`c6df948a`). A reader that ignores the optional field, as v1 allows, decodes every value of such a dataset shifted. `CATALOG_FEDERATION_PROTOCOL.md:446-448` calls a semantic change a `schema_version` bump. No bump was made, and no CHANGELOG entry written. The field doc at `src/types/color-scale.ts:49-52` still says `vmin` is the "Physical value at luma 0." Nothing emits `dataMinLuma` yet, per the commit message, so there's still time to version it properly.
  3. **The two versioning policies disagree, and one contradicts the schemas.**
     - `docs/protocol/README.md:83-92` says a break mints `/schema/v2/`.
     - `CATALOG_FEDERATION_PROTOCOL.md:438-455` says to bump `schema_version`, and to keep a removed field populated for one cycle.
     - Neither mentions the other's mechanism, or how the envelope `schema_version`, the per-row `schemaVersion`, and the `/schema/vN/` path relate.
     - `README.md:87` calls "new enum value" additive, but the generated schemas close their enums (`visibility` at `dataset.schema.json:145-153`, `renderEncoding` `const: "data-luma"` at `:229-232`). A validating reader rejects a new value. Either say readers must tolerate unknown values, or treat new values as breaking.
  4. **Wire field semantics have no published home.** `README.md:75-80` says field semantics live in `docs/CATALOG_DATA_MODEL.md`. That doc has no mention of `colorScale`, `renderEncoding`, `dataMinLuma`, `playbackFps`, `boundingBox`, `thumbnailLink`, `colorTableLink`, or `tourJsonUrl`. Its `datasets` table predates the columns that `migrations/catalog/0010_non_global_metadata.sql`, `0042_render_encoding.sql`, and `0043_playback_fps.sql` added. The schema strips comments (`jsDoc: 'none'`, `scripts/build-protocol-schemas.ts:99`). So a non-TypeScript reader gets names and types, but no decode formula and no antimeridian convention.
  5. **`?since=` never sends tombstones, though datasets can now be retracted.** `catalog.ts:29-32` and `catalog-store.ts:350-354` still say "Phase 1a has no retract path." `tombstones` is hard-coded `[]` (`catalog.ts:98, 107, 157, 166`), while `functions/api/v1/publish/datasets/[id]/retract.ts` sets `retracted_at`. A dataset that's retracted, hidden, or made non-public simply stops appearing, so a `?since=` subscriber keeps it forever. This needs fixing before Phase 4 sync relies on the cursor.
  6. **The well-known doc lags its protocol doc.** `abuse_contact` is "required — deployments without one do not federate" (`CATALOG_FEDERATION_PROTOCOL.md:43-44`), but `WellKnownDoc` has no such field (`functions/.well-known/terraviz.json.ts:45-62`). `protocol_versions_supported` and `capabilities` (`:410-415`) are missing too, and the doc's own versioning table calls the second one `protocol_capabilities[]` (`:403`). Scenario S4 is a correct additive fix for two of the three.
  7. **The conformance test the protocol relies on doesn't exist.** `CATALOG_FEDERATION_PROTOCOL.md:458-465` says a PR that breaks the (protocol, schema) matrix "has to either expand the matrix explicitly or fail." No `test:federation` script exists in `package.json`, and federation-scoping §7 Directive 4 lists it as Phase 4 work. Until then, nothing enforces the matrix.
  8. **`schema_version` has no single source.**
     - literal 1s in `catalog.ts:95, 102, 154, 161` and `tours.ts:110, 143`
     - `[1]` in the well-known doc (`terraviz.json.ts:94`)
     - the D1 defaults (`migrations/catalog/0001_init.sql:89`, `0004_tours.sql:27`)
     - an `=== 1` check in `functions/api/v1/_lib/metadata-readiness.ts:255`

     A bump has to touch about nine places, and nothing checks that they agree. Tours carry `schema_version`, and the protocol scopes it to "Dataset / Tour" (`:402`), but `/api/v1/tours` has no published schema; it isn't in `TARGETS`.
  9. **The SPA's inbound copy isn't drift-checked.** `src/services/dataService.ts:246-330` redeclares `WireDataset`, and `wireToDataset` maps it by hand. A field the server adds and the mapping omits type-checks and is silently undefined (`e3655437`).
  10. **The plugin's generated contracts are three fields behind.** `src/Contract/WireDataset.php:30` lacks `playbackFps`, `renderEncoding`, and `colorScale`. `bin/generate-contracts.php:14-15` calls for a CI drift check, but the plugin's `ci.yml` runs only the smoke suite. This is harmless today, because the plugin reads the raw array by name (`src/Contract/Wire.php:16-24`). But it shows the CHANGELOG gap reaching a consumer.
  11. **STAC will break on the next `ColorScale` field.** The native `colorScale` is open, but the STAC extension's is `additionalProperties: false` (`docs/metadata/schemas/terraviz-v1.0.0.json:75-76`), and it's served `immutable` for a year at a versioned URL (`functions/schema/stac/terraviz/v1.0.0/schema.json.ts:6-8`). `stac-builders.ts:243-245` copies the parsed `ColorScale` whole. So the next optional `ColorScale` field, additive on the native wire, makes every data-luma STAC item invalid against v1.0.0 unless the extension re-versions in the same change. Neither check links the two.
  12. **`CODEOWNERS` routes nothing.** All 29 lines are comments, while `GOVERNANCE.md:234-239` names federation identity and signing as high-scrutiny paths and admits `CODEOWNERS` is "closer to placeholder than to policy." When there's a second maintainer, candidate lines are: `public/schema/**`, `docs/protocol/**`, `functions/.well-known/**`, `functions/api/v1/_lib/dataset-serializer.ts`, `functions/api/v1/catalog.ts`, `scripts/gen-node-key.ts`, `functions/api/v1/publish/node-identity.ts`, and `docs/EMBED_URL_GRAMMAR.md`.
  13. **The embed grammar has drifted, in minor ways.** Its line citations are off: `catalogMode.ts:21-28` is now `:24-31`, and `deepLinkService.ts:72-77` is now `:75` onward. The `/dataset/<id>` path form now takes a slug, ULID, or legacy ID (`deepLinkService.ts:78`), while the grammar's table says "catalog ID," and the grammar's changelog doesn't record the widening.
  14. **The runbook's federation row had wrong and missing paths** (in this repo, not TerraViz; fixed in `7b68c2d`). It routed "`WireDataset` or any type it reaches in `src/types/index.ts`." But `WireDataset` lives in `functions/api/v1/_lib/dataset-serializer.ts`, and it reaches `src/types/color-scale.ts`, not `index.ts`. The row also omits `src/services/dataService.ts` (the inbound copy), `functions/api/v1/_lib/catalog-store.ts` (`?since=` and visibility), `scripts/gen-node-key.ts`, `functions/api/v1/publish/node-identity.ts`, and `cli/init-node.ts`.
  15. **The embed grammar should route here** (a runbook proposal; applied in `7b68c2d`). The runbook sent the embed URL grammar to the API Platform Engineer. `GOVERNANCE.md:130` lists the grammar with `/schema/v1` and the federation feed as TerraViz's published contracts, and its stability rules live in a TerraViz doc this agent rereads. Move `docs/EMBED_URL_GRAMMAR.md` and its readers to this agent. Leave the publish API, the Orbit bridge, and STAC with the API Platform Engineer. The roster entry in `strategy/runbooks.json` lands with the agent.
  16. **The full catalog stays stale after a deploy.** `/api/v1/catalog` serves a pre-rendered body from the KV key `catalog:snapshot:v1` (`functions/api/v1/_lib/snapshot.ts:32`), which has no TTL and is deleted only by publisher write paths (`dataset-mutations.ts`, `tour-mutations.ts`, the asset and transcode completions, `node-identity.ts`). No deploy step invalidates it or bumps the key. So any serializer change, additive ones included, is invisible on the full catalog until the next publish, while `/api/v1/datasets/{id}` and `?since=` serve the new shape at once. Two blind runs (S1, S2) found this independently, and the Code Reviewer baseline found it too. A key that includes a serializer version, or an invalidation in the deploy workflow, would close it.
